# project-relay v2 分叉链（卷三 3.3）

> 实现：`scripts/relay_fork.py`（标准库 only），接线进 `scripts/relay_flow.py`
> （汇总链、写前守卫、接手呈现）与 `scripts/relay.py`（目标冻结、fork CLI）。
> 本片不动核心语义：卷一只做分叉的“可见”，本片把它完善为完整链式结构；
> 汇总、目标确认（S4）、同步裁决（sync-resolve）的既有语义一律不动。

## based_on 语义

- 链的单位是**汇总记录**（`state/summaries/%04d.json`），不是单条决策/教训/待办：
  一次汇总本来就把一批追加项与条目范围打成包，记录上的指针即覆盖整批；
  追加项正文里的“汇总序号”行把它解析回所属汇总，从而解析回链位置。
- 每条汇总记录必带 `based_on`：生成它时所依据的上一条同类记录的条目 ID
  （`sum-%04d`）；链的源头（建档首条）`based_on` 为空并标注 `origin`
  （过程式/回溯式/手工：回溯建档来源为回溯式，其余为过程式）。
- `based_on` 链只增不改：任何操作（包括链压缩）都不重写已落盘的指针；
  压缩后指针靠归档包索引解析，见下。
- 链之前写下的记录（无 `based_on` 键）是**链前基底**，不是分叉、不是野分叉；
  新链从第一条带指针的记录起算，指针可以指向一条基底记录。

## 分叉定义与检测点

- 定义：读入一组记录时，若两条记录的 `based_on` 指向同一前驱、且其后
  无共同后代（两支的后代集合不相交），即构成一次分叉。
- 检测点（两处，缺一不可）：
  1. 每次接手读档（`resume`）：实时计算，不落盘——接手的零写契约优先，
     展示的永远是实时计算结果，不可能比 meta 陈旧。
  2. 每次汇总写入前（`_summarize_impl` 起手）：计算并刷新本地 meta
     （`state/forks.json`：分叉点 ID、两支的最新条目、各自来源工具与时间）。
- 支的最新条目：沿单链子节点走到头；支是汇总链时还给出条目范围。

## 呈现格式

接手输出（`resume`）在五段之后、晋升提议之前附“分叉清单”单节，
每一支写明：来源工具、最后更新时间、基于哪一版状态（`based_on` 指针）、
与主支的差异摘要。差异摘要是**字段级**的：支快照的状态卷管理块与主支
当前管理块逐字段比，只列不同的字段；汇总链支没有状态卷快照时，
差异以条目范围计并明说。干净时该节只有一行“无分叉，无待裁项”，
分叉永远不隐形，但也不刷屏。

## 取舍规则（按字段性质分，不搞一刀切）

1. 追加型内容（决策、教训、会话记录）：两支全保留。下一轮主链汇总时
   把支的追加项并入主档：按内容语义行哈希去重（两边同一句话只留一条），
   ID 冲突时重编号，支记录标记 `merged`（支快照保留作证）。
2. 状态型字段（当前进度、下一步）：不自动选边。两支的不同值并列写入
   状态卷的“分叉待裁”区（`<!-- relay:fork-pending-begin/end -->`，位于
   管理块之外，汇总重写管理块时不会抹掉它）。下一任接手 Agent 在对账
   环节拿代码现状核对后裁定：`relay fork adjudicate --fork <支id>
   --winner branch|main --note <理由>`；裁定同时改写待裁行与
   `state/fork-adjudications.json`（裁定动作记入会话记录的 durable 形式）。
3. 目标文件：永不自动合并。目标分叉即冻结目标注入（`goal_inject` 返回
   冻结提示，不给目标正文），升级为 S4 的重新确认流程：正常
   `relay goal confirm`（或 `sync-resolve --goal` 清掉同步冲突标记）
   才能解冻。目标分叉的判定：`state/goal-fork.json` 标记存在，或
   卷二的同步目标冲突标记 `state/goal-conflict.json` 存在。

## 并发写预防（写前守卫）

汇总写入前重读四个档案文件的当前哈希，与汇总开始时读到的哈希比对。
不一致（期间有人写过）时本次汇总**不直接落盘**：产物作为新的一支写入
（`state/branches/<支id>/` 快照 + `state/branches/<支id>.json` 记录，
含 `based_on`、来源、条目范围、追加项、失配文件），游标不推进、
原料条目保持 pending（主链下次汇总重消费它们，支合并按内容哈希去重，
故不重复）。宁可多一支，不可覆盖一支。守卫的重读点是
`relay_flow._read_archive_bytes`（单点，便于测试注入并发写）。

## 链压缩规程

- 阈值默认 200 条（配置 `chain_compress_threshold`，保留条数
  `chain_compress_keep` 默认 10），在一次正常汇总末尾执行。
- 折叠对象：除最近 `keep` 条外的全部 live 汇总记录，打包进
  `state/chain-archives/<锚点id>.json`（锚点 = 被折叠的最后一条），
  包内含全部记录原文与整包总哈希（记录按 seq 拼接字节的 SHA256）；
  锚点记入 `state/chain-anchor.json`，live 文件删除。
- 只动本地链结构，不改任何记录内容；`based_on` 指针不重写，
  靠包索引解析。折叠后新汇总序号仍单调（`_next_summary_seq` 计入包内 seq）。
- 安全条件：仅当无事务日志、或最新事务日志自带 `before_state` 时折叠；
  否则旧式 recover 推导会丢上一条候选，宁可不压。

## 野分叉标注

分叉检测只处理 relay 自家记录之间的分叉。用户手工编辑档案造成的野分叉
按同一检测逻辑识别：记录**带有** `based_on` 指针但对不上任何已知记录
（含包内记录）时，标注为“来源不明的一支”，处置规则与正常分叉相同
（追加项合并、状态字段待裁、目标冻结）。无指针的链前基底记录不是野分叉。

## 命令

- `relay fork list`：实时分叉清单（与接手输出同一节）。
- `relay fork adjudicate --fork <支id> --winner branch|main --note <理由>`：
  裁定一支待裁项。
- `relay fork flag-goal --reason <事由>`：标记目标分叉（冻结注入），
  解冻走正常目标确认或同步目标裁决。
